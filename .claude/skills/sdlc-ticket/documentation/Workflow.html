Principes transversaux

  • Humain cadre, machine génère. L'humain pose l'intention et tranche ; la machine produit le volume et exécute. On n'inverse jamais ces rôles.
  • Les barrières suivent le risque, pas l'étape. On met le jugement humain là où une erreur coûte le plus cher : priorité, fusion, sécurité. Un ticket à faible risque passe sans barrière de plan.
  • Connaissance contraignante ≠ référence. Contraignante → poussée, toujours en contexte, verbatim (jamais résumée par un petit modèle). Référence → tirée, recherchée à la demande.
  • Flux ≠ connaissance durable. Tickets/backlog portent le flux ; le registre de décision porte la connaissance. Deux outils, deux modèles mentaux.

Les barrières (gates)

Toute intervention humaine n'est pas une barrière. Distinguer la nature, c'est savoir quoi automatiser — seules les barrières bloquantes deviennent un gate Jira.

NatureComportementComment ça s'automatise
⛔ BarrièreLa machine s'arrête et attend une approbation.Statut « en attente d'approbation » + transition gardée par rôle.
⇄ RoutageDécision qui aiguille ; n'arrête pas la machine.Règle de triage automatique + override humain.
⏲ CadenceRythme planifié, pas lié à un ticket.Déclencheur planifié / tâche récurrente.
✎ CadrageL'humain alimente l'entrée d'une étape.Champ d'entrée — aucun blocage à automatiser.

Du workflow au ticket : deux altitudes

Le même système vu de deux hauteurs. Le vocabulaire se répète exprès (« plan », « backlog », « priorité ») ; voici la correspondance.

AltitudeÉtapesBarrières
Feature (epic, pré-sprint)①②③G1 PRD (①) · G2 stamp du plan-feature (②) · découpage (③)
Ticket (chaque enfant, dans ⑤)pipeline 6-statuts du skillpriorité (Backlog→Ready) · plan d'exécution · revue+fusion · validation PO
  • « Plan » apparaît deux fois, exprès : le plan de feature (② — comment aborder la feature, stampé par le TL) ≠ le plan d'exécution par ticket (dans ⑤ — DoD/fichiers/tests, approuvé au gate). risk:low saute le plan d'exécution, pas le stamp de feature.
  • « Backlog » a deux sens : l'étape macro ③ (découpage) et le statut Backlog d'un ticket (créé, en attente de priorité). Le passage Backlog→Ready d'un ticket vit dans la préparation (①–③), pas dans ⑤.
  • « priorité » vs « prioriser » : la barrière priorité = transition Backlog→Ready (le ticket est approuvé) ; le « choix du ticket » en ⑤ = sélection de sprint parmi les Ready (cadrage), un acte distinct.
  • 4 barrières à chaque altitude : au niveau feature, G1–G4 (PRD / stamp du plan / revue+fusion / validation prod) ; au niveau ticket, le skill en porte aussi 4 (priorité / plan d'exécution / revue+fusion / validation PO). La validation PO du ticket est le petit frère du G4 feature.
1

Carnet de produit

PO + IA
Cadrage (humain)
Le PO décrit l'intention et la valeur de la feature.
Machine
Skill « carnet de produit » : génère feature request + PRD ; flag explicite des inconnues.
Barrière ⛔
Le PO valide le PRD. Écueil : surveiller l'altitude — rester produit, ne pas dériver vers la solution.
Artefact : PRD + feature request, inconnues signalées.
Détails
Ce que contient un PRD :
  • Problème et utilisateur visé · valeur attendue
  • COS (critères de succès vérifiables)
  • Portée et hors-portée explicites
  • Inconnues signalées — ce qu'on ne sait pas encore, rendu visible pour les étapes suivantes plutôt que deviné
Idée brute (pas encore une spec) : explorer d'abord — brainstorm coaché / brief / PRFAQ (working backwards). Chaque idée vient de l'humain ; l'agent facilite, ne pitche pas. Sortie = un brief qui alimente le PRD. Voie rapide : si la conversation contient déjà le problème, la direction et les contraintes, on synthétise le brief sans ré-interroger — inutile de redemander ce qui est sur la table.
Granularité flexible : tout n'est pas un epic. Epic (feature multi-sprint) → PRD complet. Story → « PRD » léger = description enrichie (problème + COS). Tâche simple → pas de PRD, G1 peut être sauté (comme risk:low). La barrière existe toujours ; son poids suit la taille.
Déclenchement (V0) : manuel — le PO/dev demande à Claude de créer l'unité (epic/story) ; le skill démarre via le MCP Atlassian.
Écueil d'altitude : le skill doit rester au niveau produit (le quoi/pourquoi). Dès qu'il propose une solution technique, il a trop descendu — c'est le rôle de l'étape ② Plan.
2

Plan

TL
Cadrage (humain)
L'humain soumet les grandes lignes du plan — brainstorm.
Machine
Génère plusieurs variantes de plan ; un agent arbitre ressort le meilleur.
Barrière ⛔
Stamp TL + équipe avant tout code. Modulée par le risque.
Artefact : plan d'exécution validé.
Détails
Patron brainstorm → arbitrage :
  • L'humain donne les grandes lignes (contraintes, intention), pas un plan fini.
  • La machine génère N variantes sous des angles différents (MVP d'abord, risque d'abord, etc.).
  • Un agent arbitre sélectionne / fusionne la meilleure variante et justifie le choix.
  • Stamp = le TL et l'équipe valident le plan retenu → ça devient la barrière de plan du pipeline (étape ⑤).
Modulation par le risque : un plan étiqueté risk:low peut être pré-approuvé et sauter la barrière humaine de plan en aval.

Backlog

Jira · +++ machine
Cadrage (humain)
Cadre l'intention ; valide la découpe.
Machine
Propose le découpage épic → story → tâche → sous-tâche (bonne grosseur), l'ordre et les dépendances ; rédige description / COS.
Routage ⇄ — filtre & classification (non bloquant)
Simple → machine seule.   Complexe → co-work machine + humain.
Artefact : backlog Jira découpé, dimensionné, ordonné (dépendances) et classé simple / complexe.
Détails
Découpage de la fonctionnalité (machine propose, humain valide) :
  • Hiérarchie : épic → story → tâche → sous-tâche.
  • Tranches verticales (règle n°1) : 1 ticket = 1 tracer bullet — une tranche fine qui traverse toutes les couches qu'elle touche (schéma → backend → UI → tests), démontrable seule. Pas une tranche horizontale d'une seule couche : un ticket « schéma seul » arrive en PO review sans rien à démontrer, alors que le gate G4 exige les COS depuis la sortie utilisateur. Coût toujours borné à une PR revue d'un coup d'œil (~≤ 400 lignes) ; trop gros → tranche plus étroite mais toujours de bout en bout. Ni sur-découpé : une colonne + sa migration = un seul ticket.
  • Préfactoring d'abord : « rends le changement facile, puis fais le changement facile » — si les tranches ont besoin d'un socle (extraire un seam, remodeler une interface), c'est le premier ticket. Ordre par dépendance, jamais par couche ; l'ordre des couches (schéma → backend → UI → agrégat) ne sert qu'à sous-découper une tranche devenue trop grosse. Jamais dépendre d'une story ultérieure.
  • Dépendances : liens Jira blocked by / blocks / relates to → graphe d'exécution + ordre de prise (vérifier l'acyclicité).
  • AC vérifiables uniquement : « ajoute la colonne X (défaut Y) », pas « fonctionne bien » / « gère les cas limites ».
  • Tout ça se fait en préparation : un ticket n'entre dans le sprint (⑤) que découpé et ordonné.
Critères de classification (qui tranche : l'humain) :
Simple → machineComplexe → co-work
Périmètre clair, isoléAmbigu ou transverse
Faible risque, pas de décision d'archiRisque, sécurité, ou décision d'architecture
COS évidentsCOS à négocier avec l'humain
Verdict de préparation (avant le gate priorité) : le découpage se clôt par un verdict PASS / CONCERNS / FAIL sur l'epic. En priorisant les enfants, l'humain approuve d'un coup brief + PRD + découpage — le verdict rend visible toute faiblesse (story trop grosse, AC non vérifiable, cycle de dépendances, hypothèse non validée). FAIL → on ne demande pas le gate, on corrige.
Context-mémo par ticket — revue registre + Confluence, faite une fois : à la création, l'agent interroge le registre de décision et la doc Confluence selon les composants du ticket, et écrit le résultat dans l'entity property Jira agent-context :
  • Contraignant → verbatim : {id, règle, date} — jamais résumé.
  • Référence → résumé + lien Confluence.
Ainsi l'agent d'exécution (⑤) n'a plus à relire la doc à chaque itération — le contexte est déjà dans le ticket.
Péremption : ③ est pré-sprint, ⑤ vient plus tard — d'où les dates + IDs : à la prise, l'agent revalide seulement qu'aucune décision n'a été remplacée (comparaison de dates, pas de relecture complète). (entity property : API, invisible aux humains, ≤ 32 Ko, lisible par tout utilisateur authentifié — rien de sensible.)
Fallback : si l'écriture d'entity properties est bloquée chez le client (pas de token API), le même payload va en bloc de commentaire HTML <!-- sdlc:context --> en fin de description du ticket. Les lecteurs vérifient la property d'abord, puis la description.

Hebdomadaire
Cadrage (humain)
Passe humaine 1× par semaine.
Machine
Tient à jour le registre de décision et le registre de sécurité ; met à jour le backlog non-actif.
Cadence ⏲ — revue hebdo (pas un gate par ticket)
L'humain valide les décisions consignées. Capture réunion → l'agent rédige → 👍 → consigné.
Artefact : registre à jour — partie contraignante poussée en contexte, partie référence consultable.

  • Registre de sécurité : même schéma, revue séparée — les décisions de sécurité sont contraignantes par défaut.
  • Capture sans cérémonie : une décision de réunion n'a pas de PR de code → l'agent rédige l'entrée, un 👍 humain la consigne (barrière légère, pas de revue de code).
  • « Forcer une convention de travail ? » — oui pour le contraignant (poussé déterministe­ment, pas une consigne polie) ; inutile pour la référence.
  • Mémoire patterns (cross-ticket) : les apprentissages réutilisables vont dans une mémoire append-only ; un pattern éprouvé sur quelques tickets est promu dans le registre contraignant / AGENTS.md via un ticket gated. Working memory ≠ gospel.
  • La promotion est un pas obligatoire du Done, pas du best-effort : le commentaire de clôture de chaque ticket contient une section learnings: — items promouvables (avec leur maison cible) ou le mot explicite none. C'est ce qui amorce le registre ; le sauter est le mode d'échec « démarrage à froid ».
  • Rétrospective agent (retro:) au même endroit : deux questions fixes que l'agent se pose à la clôture — (1) qu'est-ce qui aurait rendu ce ticket plus rapide/meilleur (contexte manquant au mémo, COS ambigu, trou dans le skill)? (2) qu'est-ce que les humains devraient changer (process, config, rédaction du ticket)? L'introspection porte sur la collaboration, pas sur le code, et chaque item est formulé comme un changement concret applicable (quel fichier, quelle modification) — pas un constat. Le V0 interactif permet de fermer la boucle sur-le-champ : l'agent propose d'appliquer les changements tout de suite ; l'humain approuve → le skill/config/template est patché dans la même session (item marqué applied). Les items non appliqués vont à la revue hebdo ; un item récurrent = arrêter de le noter, le patcher.

BLOCKED est transversal : un humain y déplace tout ticket actif qui heurte un bloqueur ouvert, et le ramène par contexte. L'agent garde son label et s'arrête.

  • needs:human = l'agent s'est arrêté, la balle est à l'humain. La colonne désambiguïse : en planning = approbation du plan ; en building = revue de PR.
  • Une fois needs:human posé, l'agent ne pousse plus de commit (sinon l'humain revoit une cible mouvante).
  • Gate local avant PR (miroir CI) : type-check + lint + test au vert.
  • Revue IA = cross-model (Codex revoit le diff de manière adverse : exactitude, sécurité, couverture). C'est un prérequis du SDLC, pas une option : un environnement qui interdit l'envoi de code à un modèle externe n'est pas compatible avec ce SDLC — on ne construit pas de variante dégradée.
  • Règle dure : l'agent ne fusionne jamais ; la fusion (squash) reste humaine.

Bonnes pratiques d'exécution

  • Le thread du ticket = la mémoire. Chaque étape poste un commentaire marqué avant de bouger le label ; toute reprise lit tableau + thread (pas la conversation). N'importe quelle session reprend un ticket en vol.
  • Prise dépendance-aware : zéro bloqueur ouvert avant de réclamer (colonne = priorité, pas faisabilité) ; sélection = en-vol d'abord, puis priorité, puis pouvoir de déblocage.
  • Choix du seam de test d'abord : où la feature est exercée — réutiliser un seam existant, le plus haut possible, le moins de seams (idéal : un). L'agent d'exécution teste à travers lui ; un mauvais seam = une réécriture.
  • Grilling des décisions ouvertes (tickets complexes, interactif, avant le pré-mortem) : mettre à l'humain une question à la fois, chacune avec la réponse recommandée ; chercher les faits dans le code soi-même, ne soumettre que les décisions. Extrait le contexte humain que le pré-mortem (contexte interne) et Codex (contexte neuf) ratent tous deux.
  • Pré-mortem sur le plan (avant Codex) : « suppose que ça a été rejeté — pourquoi ? », puis patcher.
  • Triage des findings : bloquant → corrige dans la PR ; incident → ticket backlog ; rejeté → raison. Aucun finding ignoré en silence.
  • Correct-course : sur rejet, régénérer depuis la couche fautive — intention / plan / implémentation — jamais patcher en bas.
  • Review-guide : le « prêt pour revue » est un walkthrough par risque, pas un pointeur sur le diff.

Où vit le skill — le mécanisme de fork

Le skill est l'actif réutilisable ; sa copie dans chaque projet est un point de fork assumé, pas une dérive.

QuoiOù / comment
Version canoniqueLe registre py-moov (skills/project/) — c'est là que le skill est versionné et amélioré pour tous.
Copie de travailDans chaque projet (.claude/skills/), installée via moov skills install. L'adapter aux règles internes / client est attendu — c'est la raison d'être du modèle par projet.
Mise à jourmoov skills update détecte les éditions locales (hash de contenu) et les protège : un skill modifié localement est sauté sauf --force. Une copie divergente n'est jamais écrasée en silence.
RemontéeUne amélioration qui généralise (pas spécifique au client) remonte au registre py-moov via PR — c'est ainsi que les 10 équipes capitalisent sans centraliser.
En clair : si la copie de ton projet diffère du registre, ce n'est pas une erreur à « corriger » — c'est probablement une adaptation client voulue. Lis le diff avant de forcer une mise à jour.

Vers l'automatisation

Maintenant que les barrières sont nettes, chaque couche a un rôle clair. Le détail viendra plus tard.

V0 — démarrage manuel, zéro custom code : tout est déclenché par un dev/PO dans Claude Code via le MCP Atlassian (« crée un epic », « prends le prochain ticket », « fais la revue hebdo »). Seules les couches Jira et Skills sont nécessaires. Le custom code vient quand le flux manuel a fait ses preuves.
CoucheCe qu'elle porte
Jirales statuts + transitions gardées (barrières ⛔), les règles de triage (routage ⇄), les déclencheurs planifiés (cadence ⏲)
Skillsce que la machine génère/exécute à chaque étape (carnet de produit, plan, revue cross-model, capture de décision…)
Custom code (plus tard)la colle : webhooks Jira ↔ agents, injection du registre contraignant en contexte, déréférencement des pointeurs (context-mémo → registre)
Règle d'or pour l'automatisation : une barrière ⛔ = un statut Jira où l'agent s'arrête et ne fait plus rien jusqu'à la décision humaine. Tout le reste (génération, revue IA, déplacement de labels) est automatique de barrière en barrière.
