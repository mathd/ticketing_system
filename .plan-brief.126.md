## The ticket

**Summary:** One domain-event envelope in `shared/go` — the type and ADR-017's decode rules are
re-implemented at 6+ sites.

**Finding (architecture review R3, 2026-07-25).** The platform envelope is declared independently at:

| Site | Form |
|---|---|
| `services/catalog/internal/events/events.go:32` | full `Envelope` struct (`ID string`) |
| `services/commerce/internal/events/events.go:17` | full `Envelope` struct (`ID uuid.UUID`) |
| `services/access/internal/consumer/consumer.go` | 3 partial structs: `FailureEvent` (:44), `envelope` (:156), `completed` (:171) |
| `services/inventory/internal/consumer/consumer.go` | 2 partial structs: `publication` (:62-75), `envelope` (:176) |
| `services/access/internal/store/{scan.go:366,lifecycle.go:368,reconcile.go:311}` | inline anonymous structs marshalled into the alarm outbox |

ADR-017's two load-bearing rules — **dispatch on `schema` before decoding `data`**, and
**`schema <= 0` is a broken envelope, not the future** — are therefore re-derived at each decode
site. `AGENTS.md` records the consequence: **TKT-61 shipped the ordering bug twice**, past a
mutation-checked test suite and a full review pass. Duplication is the mechanism.

This is the one place the review recommends *adding* to `shared/go` despite the thin-kernel rule.

**The trap this ticket must not fall into.** ADR-017 names it: *a fixture built from the type under
test cannot fail* — it encodes the compatibility it claims to prove. The golden bytes proving the
wire is unchanged must be **captured from the current emitters before the refactor and pinned as
literals**. Regenerating them from the new shared type proves nothing.

## Conditions of Success (COS — these are the acceptance criteria)

1. **One `Envelope` declaration remains repo-wide**; per-subject payload types stay in their owning
   service. (Check: a grep for `json:"schema"` finds the shared type and per-subject payloads, not
   competing envelopes.)
2. **`DecodeEnvelope` enforces `schema`-first dispatch and rejects `schema <= 0`** as a broken
   envelope (terminate; **must not touch readiness**). Both have tests.
3. **Golden literals captured from the pre-refactor emitters** prove every published subject is
   byte-for-byte identical afterwards — and those literals are **not** generated from the new type.
4. **An ADR records the `shared/go` addition** — it lands in this ticket, not a follow-up.
5. **`make check` green** with the existing event/consumer suites **unmodified**.

## Scope (from the ticket's DoR)

**IN:** an `Envelope` type + a `DecodeEnvelope` helper in `shared/go` enforcing ADR-017 §5b′ and the
bottom end; replacing the local declarations at every site in the table; the ADR.
**OUT:** per-subject payload types (they stay in their owning service); the consumer run-loop
skeleton (that is TKT-127, which this ticket blocks); **any wire change**.

**First slice (as shaped):** shared type + `DecodeEnvelope` + the ADR + migrating the two publisher
sites (catalog, commerce) with byte-identical golden proof. The consumer-side decode sites may
follow **in the same PR if the diff stays inside a ~400-line budget**; if not, split the consumer
migration out into a follow-up ticket. *Your plan must make this call explicitly and justify it.*

## The one open decision handed to you (DoR `uncertainties`, deferred to plan time)

**Do the deterministic-id / dedup-key helpers move with the envelope, or stay per-service?**
Catalog derives ids five different ways — `EventID`, `BackfillEventID`, `ArchivedEventID`,
`ClosureEventID`, `SeatMapPublishedEventID` — each with a domain-specific key string; commerce has
its own `EventID(orderID)`. All six are `uuid.NewSHA1(uuid.NameSpaceOID, []byte(key)).String()`
over a different key. The shared piece may be only the SHA1-over-key primitive, or nothing at all.
**Make a recommendation with a reason.** No COS depends on it.

## Governing ADRs — what each constrains *for this ticket*

Re-resolved against `docs/adr/` at claim time (latest is ADR-032; nothing landed between shaping
and claim that touches this area).

- **ADR-017 — domain-event schema evolution** (`docs/adr/ADR-017-domain-event-schema-evolution.md`).
  The decision being centralized. §5b′: **a consumer must dispatch on `schema` before decoding
  `data`** — a bump exists *because* `data` changed, so judging a future variant with today's struct
  rejects it as malformed and drops it. The poison/skew line has a **bottom end**: `schema <= 0` is a
  broken envelope, not the future — **terminate it, and do not let it touch readiness**. And: a
  fixture built from the type under test cannot fail. Read §3, §4, §5b, §5b′ before drafting.
- **ADR-009 — contract-first APIs** (`docs/adr/ADR-009-contract-first-apis.md`). §5 fixes the
  envelope *shape as contract*: `id`, `type == subject`, `occurred_at`, `schema`, `data`, published
  to JetStream **with acks**, with a **deterministic envelope id** so retried/raced emissions
  de-duplicate. The field set and JSON key order are contract — the refactor must not perturb them.
- **`docs/architecture.md:74`** — *"`shared/go` | shared kernel: healthz contract (`httpx`),
  observability (`obs`) — **additions require an ADR**"*. This is the working-agreement rule that
  puts COS-4 in scope. (ADR-002 establishes the five-services-plus-shared layout; the
  additions-require-an-ADR sentence is the architecture doc's.) Your ADR must argue why the envelope
  earns its way into a deliberately thin kernel.
- **ADR-025 — admission events & offline reconciliation**. The three inline structs in
  `services/access/internal/store/` are **alarm** envelopes written to
  `lifecycle_integrity_alarm_outbox`. §D9 constrains alarm payloads to *"identifiers and enums
  only"* (there is an open backlog ticket, TKT-120, disputing whether the shipped payload honours
  it). Migrating those three sites must **not** change the alarm payload — the `Data` types
  (`policyConflictAlarmData`, `alarmData`, `conflictAlarmData`) stay exactly as they are; only the
  envelope wrapper changes. Do not "fix" TKT-120 here.
- **ADR-021 — ticket-lifecycle trail integrity** (context only): the alarm outbox rows are part of
  the access integrity surface. Byte-identical means byte-identical there too.

## Code facts already verified at HEAD (`git grep`/read — trust these, but re-read the files)

1. **The two publisher `Envelope` structs differ in the Go type of `ID`**: catalog is
   `ID string` (its `EventID`-family helpers return `string`), commerce is `ID uuid.UUID`.
   Both marshal to the same JSON string, so the *wire* is unaffected — but a single shared struct
   must pick one, and the losing side needs call-site adaptation. **Say which, and why.**
2. **Emit-side and decode-side want different `Data` types.** Every emitter marshals a *typed*
   `Data` (or `any`); every decoder needs `Data json.RawMessage` so `data` stays undecoded until
   `schema` has been dispatched on. One struct cannot serve both cleanly. Consider whether the
   shared package needs **two** types (an emit `Envelope` and a decode view) or a generic — and note
   that **`Data json.RawMessage` on the emit side would silently change nothing on the wire only if
   callers pre-marshal**, which is a call-site change at every emitter. Weigh it.
3. **Field order in the Go struct is the JSON key order** (`encoding/json` emits in declaration
   order). Every existing site declares `id, type, occurred_at, schema, data` — except the two
   consumer decode structs, which omit fields they don't read. The shared emit type must keep that
   exact declaration order or the golden bytes change.
4. **`services/access/internal/consumer/consumer.go:44` `FailureEvent`** is an *emitter* envelope
   (subject `platform.access.ticket-issuance.failed`) that happens to live in the consumer package.
   It is a 6th emit site the ticket's table folds into "3 partial decode structs" — decide whether it
   migrates too and say so.
5. **`inventory`'s `publication` (:62) and `access`'s `completed` (:171) are second-pass decode
   structs**: they redeclare `id`/`type`/`schema` *alongside* a typed `data`. They are the per-subject
   payload types the scope says stay in their owning service — but their **envelope fields** are
   duplication. Decide: embed the shared type, or leave them whole. Justify.
6. **Existing test seams.** `services/catalog/internal/events/events_test.go` has 11 tests over the
   envelope (`TestPerformancePublishedEnvelopeSchemas`, `TestSeatMapPublishedEnvelope`,
   `TestBackfillEnvelopeCarriesDistinctIDAndCurrentReEntry`, …) and calls the **unexported**
   `performancePublishedEnvelope` / `performanceArchivedEnvelope` / `seatMapPublishedEnvelope`
   helpers directly — an in-package seam that already marshals real bytes.
   **`services/commerce/internal/events/` has NO test file** — commerce's `OrderCompleted` marshals
   inline in the publish method with `time.Now().UTC()`, so it has no pure-bytes seam yet.
   Consumers: `services/inventory/internal/consumer/` and `services/access/internal/consumer/` have
   handler tests driving a fake `jetstream.Msg`. Name the seam(s) you pick and confirm each exists.
7. **Modules.** `go.work` uses `./gateway ./services/{access,catalog,commerce,inventory,payments}
   ./shared/go ./smoke` — 8 modules. `shared/go` today holds `httpx`, `obs`, `contract`,
   `runtimecfg`, `fakepsp`. Adding a package there means every consuming module's `go.mod` needs the
   dependency (check how existing modules require `shared/go` — replace directives or workspace?).
   **This is a real mechanical risk: name it and say how the plan handles it.**
8. **The local gate is `make check`** (lint + test + build, Go & TS, plus a gateway smoke suite).
   Generated files (`openapi_gen.go`, `api-types.gen.ts`) must be **committed before** running the
   gate — `check-generate` diffs against `HEAD`. This ticket should not touch generated code, but
   say so explicitly if you believe otherwise.
