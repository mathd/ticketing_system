# Code Review

**Date**: 2026-08-28
**Scope**: Full codebase — services/{catalog,inventory,commerce,payments,access}, gateway, shared/go, smoke, scripts, web/{backoffice,storefront,scanner}, test/browser. Nine parallel review passes (one per subsystem plus architecture and documentation, reported separately), every finding verified against the code it cites.

## Summary

The code is in better shape than a 280-ticket accretion has any right to be. Locking discipline, money arithmetic, idempotency, and the append-path/lifecycle rules hold everywhere they were checked, and the test suites largely pass the repo's own "can this fixture reach the failing state" bar. The dominant defect pattern is not entropy but **incomplete sweeps**: a hard-won rule gets established in one file (framed fingerprints, the reseller-scope column, ADR-062's lease sizing, the storefront's monotonic clock, the admission union, strict tsconfig) and its siblings keep the old behaviour. Almost every Critical and Important finding below is an instance of that shape.

## Strengths

- Money is integer minor units everywhere, with checked arithmetic and exact-decomposition allocation; no float was found on any money path in any service.
- Locking and clock discipline are uniform and argued in place: pool-row-first ordering in inventory, ADR-018 row locks in catalog, id-ordered ticket locks in access, family advisory locks per ADR-029.
- The lifecycle trail's append-path discipline is real: `appendLifecycle` is the only production inserter, both verifiers assert coverage in both directions, and the ADR-021 rollback-gap pin test executes the fraud it documents.
- Idempotency is structural, not bolted on: deterministic fact ids, replay-before-eligibility, fingerprints that refuse key reuse with different terms.
- Test quality is far above the norm. The reviewers went looking for the repo's documented pathologies (fixtures that cannot fail, decorative seeds, harness-pinning assertions) and found almost none live; several suites are explicitly built so deleting a predicate goes red.
- Load-bearing comments. In every case checked, in-code rationale named the right adversary, clock, and pinning test. That is also why the comment-rot findings below matter more here than elsewhere.

## Recommendations

### Critical (Must Fix)

- [ ] **R1** — Hold retry with a presale code against an ungated channel is refused instead of replayed: `CreateHold` compares the replay fingerprint computed from the raw code (`services/inventory/internal/store/store.go:473`) but stores one computed after the code is cleared (`store.go:589-595,656`). First request succeeds, the identical retry gets `ErrIdempotency` 409 — a leaked hold plus a failed checkout retry on the buyer path. `PlaceGroupReservation` computes the fingerprint once, pre-clear (`reservations.go:51-55`); do the same. No test retries a key on this path.
- [ ] **R2** — Staff-operation claim keys live in the public idempotency namespace via string prefixes (`op-place:`, `convert:`, `grp-place:`, `grp-draw:` — `services/inventory/internal/store/operational.go:186,342`, `reservations.go:211,325`). These rows carry `reseller_scope` NULL, so they share `claims_public_idempotency` with arbitrary public keys; a public caller who submits `Idempotency-Key: op-place:X` permanently occupies that key and a later staff operation with key `X` answers an unmapped 500, forever. Migration 0016's own comment condemns exactly this pattern; the fix reached reseller scoping but not the four staff prefixes.
- [ ] **R3** — Int64 overflow in the refund-leg ceiling bypasses `ErrRefundExceedsCapture`: `bound.Int64+amount > captured.Int64` is unchecked Go addition and `amount` has only `> 0` enforced (`services/payments/internal/store/refund_legs.go:127`; OpenAPI has no maximum, `api/openapi.yaml:373`). A near-`MaxInt64` leg wraps negative, passes the ceiling, inserts, and against the fake PSP appends a `payment.refunded` fact for more than was captured. The ceiling is the mechanism ADR-037 §4 rests on.
- [ ] **R4** — Exchange's admitted-check reads only half of the admission union: `ticketAdmitted` (`services/access/internal/store/exchanges.go:219-225`) consults only `lifecycle_events`, but ADR-025 §D2 defines admission history as trail ∪ quarantine. A ticket admitted through a corrupt chain (quarantine-side `admitted_at`) reads as unadmitted, so `SwitchExchange` voids it and issues a fresh unredeemed replacement — the double admission `ErrSourceTicketsAlreadyAdmitted` exists to prevent. Both existing tests admit via the trail; neither covers the quarantine side.

### Important (Should Fix)

- [ ] **R5** — A crashed successful `fake-ok` charge can never be status-resolved: `Fake.Status` returns `Captured` with `Confirmed: nil` (`services/payments/internal/psp/fake.go:83-95`) and TKT-257's guard refuses any Captured resolution without an agreeing confirmation (`api/psp.go:181-184`, `port.go:137-141`). Commerce's recovery runner parks the order permanently. No test exercises status resolution of an unresolved fake success.
- [ ] **R6** — The charge boundary admits `amount == 0` (`services/payments/internal/api/server.go:271` checks `< 0`), which binds an operation and calls the provider for a charge the journal can never record (`store.go:246` requires strictly positive facts); the operation ends permanently bound-unresolved. Align the boundary check with the durable layer's positivity rule.
- [ ] **R7** — The bulk-refund runner's lease is sized from the wrong timeout — the exact defect ADR-062 ai-review F1 fixed in its two siblings: `cmd/commerce/main.go:410-412` passes `recoveryCallTimeout` (10s) but the runner drives refunds through `obs.Client()` at 30s, so a batch can outlive its lease and a successor reclaims rows still being driven. Reversal and exchangesweep both pin this rule with a test; nothing pins the bulkrefund call site.
- [ ] **R8** — A parked resumable order re-enters the money path on buyer replay: a parked `created`/`payment_unknown`/`confirmation_pending` order falls past every replay branch in checkout and resumes full orchestration including the payments charge (`services/commerce/internal/api/server.go:1421-1436`, reached via `:1671-1748`; only `release_pending` consults `recoveryParked`). The code's own comment classifies it high and says "tracked as its own ticket" — verify that ticket exists, or open it.
- [ ] **R9** — Exchange upgrades hard-code the fake PSP's approve token: `settleExchangeDelta` submits `"payment_token": "fake-ok"` (`services/commerce/internal/api/exchanges.go:580`), so no buyer instrument is ever collected for an upgrade and a real PSP silently cannot charge anyone. Unlike the mail fake, this deferred decision is recorded in no ADR. (See the architecture review's R1 for the companion checkout-side coupling.)
- [ ] **R10** — Allocation release-time edits are interpreted in the server's timezone: `allocation-form.ts:144-157` (web/backoffice) parses `datetime-local` with `new Date(value)` and renders with `getHours()`, both in the SSR process's zone, so an operator's edited `release_at` shifts by (server TZ − operator TZ). The repo's own rule refuses bare `datetime-local` for exactly this reason (`events/new.astro:264-266`), yet `slots/[id].astro:286-292` ships one.
- [ ] **R11** — Channel rename silently reverts a concurrent toggle: the rename form snapshots `enabled`/`kind`/`code` into hidden inputs and PUTs the full replacement with no optimistic token (`web/backoffice/src/pages/channels.astro:207-232`). Operator B disables the channel, operator A renames, and A's stale hidden `enabled="true"` re-enables it with a 303 reporting success. The TKT-250 revision pattern was applied to allocations and not here; the browser spec is single-actor so it cannot see it.
- [ ] **R12** — Back-office session expiry still uses the wall clock the storefront abandoned as a defect: `web/backoffice/src/lib/session.ts:82,163` uses `Date.now()` while `web/storefront/src/lib/session.ts:153-155` documents (TKT-220) why a backwards clock step resurrects an expired-but-never-presented token. The back office is the higher-value target and its comment at `session.ts:168-170` claims a protection that does not cover this case.
- [ ] **R13** — The scanner compiles without `strict`: no scanner tsconfig sets it (`web/scanner/tsconfig.app.json`), while both Astro apps extend `astro/tsconfigs/strict`. `strictNullChecks` is off for the one app running at a live gate.
- [ ] **R14** — Back-office smoke suites skip instead of failing when staff credentials are absent: `staffCredential`/`roleCredential` call `t.Skip` (19 sites, e.g. `smoke/backoffice_venue_list_test.go:257-259`). Today's `scripts/smoke.sh` provisions them, but nothing asserts they arrived, so a provisioning refactor silently drops the whole back-office role matrix while the gate stays green — against the suite's own stated "t.Fatal, never t.Skip" rule (`smoke/channel_registry_lookup_test.go:93`).
- [ ] **R15** — `obs.Client()` rides untuned `http.DefaultTransport` (`shared/go/obs/obs.go:73-79`): `DefaultMaxIdleConnsPerHost` is 2, so under on-sale concurrency the checkout → inventory/payments hops open and discard a TCP connection per request. The gateway tunes its transport for exactly this reason (`gateway/cmd/gateway/main.go:252-270`); the same argument was never applied one hop later.
- [ ] **R16** — The presale-code operator surface does not exist: `IssuePresaleCode` and `PresaleCodeStatuses` have no callers outside tests (`services/inventory/internal/store/presale_codes.go:122,177`) — no route, no OpenAPI path, no CLI subcommand. ADR-064 says issuance is API-only but no API shipped, so gated channels can only be configured by hand-writing `presale_codes`. Either ship the endpoint or pin the gap.
