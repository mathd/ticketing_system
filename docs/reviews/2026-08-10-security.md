# Security Review

**Date**: 2026-08-10
**Scope**: Full codebase — gateway, 5 Go services (catalog, inventory, commerce, payments, access), 3 web frontends (backoffice, storefront, scanner), shared libs, compose/deploy, CI workflows. Dependency audit included (govulncheck on all 7 Go modules, pnpm audit).
**OWASP Alignment**: Top 10:2025

## Summary

The security posture is strong for a testbed: no SQL injection, XSS, SSRF, path
traversal, command injection, open redirects, or unsafe deserialization was found —
several of these are closed by commented, test-pinned design rather than by accident.
The dependency audit is clean (govulncheck: 0 reachable findings across all modules;
pnpm audit: 0). The real exposure concentrates on the **access service's public edge**:
scan writes accept no credential, and ticket bundles + QR images are served to anyone
holding a link-shared order reference. Both are known and deferred in-repo (TKT-19,
TKT-222) — this review confirms the gaps are real and rates them against the current
deployment model (loopback-only, plain HTTP, compose-default signing keys), under
which the two critical findings are exploitable by anyone on the local network today.

**Findings: 2 critical, 5 important, 7 suggestions.**

**Status (2026-08-10).** Every finding was re-checked against the code before any
change; all fourteen claims held. **All fourteen are now fixed** — `make check`
and `make browser` both pass.

Three deviate from the fix the review proposed, because the proposed fix does not
work as written. Each is argued where it lands, and
[the deferred write-up](2026-08-10-security-deferred.md) records the decisions:

- **S1** — not an `X-Scanner-Token` shared by every gate: the scanner is a static
  SPA, so that token ships in a public JavaScript bundle. Per-device enrolment
  instead (`access enrol-scanner`), revocable per device.
- **S7** — no limiter on inventory's `POST /holds`: commerce is that route's
  dominant caller, so a source-keyed bucket there would throttle every real
  checkout. And per-buyer hold concurrency has no buyer to key on — guest reserve
  mints a synthetic buyer per reservation. Both gaps are named in
  [ADR-055](../adr/ADR-055-on-sale-write-rate-limiting.md) rather than left silent.
- **S13** — the currency assumption is pinned at the JOURNAL boundary, which is
  where it becomes permanent, rather than only at the charge boundary that already
  hard-coded EUR.

## Strengths

- **Injection surface verified closed.** All SQL is parameterized; the one string-
  composed query (`services/catalog/internal/store/postgres.go:1295-1315`) folds
  compile-time constants only. No `set:html`/`dangerouslySetInnerHTML` anywhere; all
  rendering is framework-escaped. No user-controlled URL is ever fetched server-side.
  No `os/exec` in production code. No open redirect — every redirect target is a
  hard-coded path, with the phishing rationale in comments.
- **Credential hygiene.** `.env` is gitignored and never committed (history checked);
  `INTERNAL_SERVICE_TOKEN` and the staff write tokens have no defaults, fail fast via
  `runtimecfg.RequiredCredential` (which also refuses the retired literal forever,
  `shared/go/runtimecfg/runtimecfg.go:91,102-138`), and are generated per-clone by
  `make up`. Services refuse to boot when credentials are pairwise-equal.
- **Password handling is textbook.** bcrypt cost 10, 72-byte bound enforced *before*
  the DB lookup, dummy-hash comparison for unknown identifiers, one shared refusal
  body for unknown-user vs wrong-password. Reset tokens are 256-bit, SHA-256-hashed at
  rest, single-use, with a server-configured (never Host-derived) link base
  (`services/commerce/internal/store/password_reset.go`).
- **Session/CSRF construction.** HttpOnly + SameSite=Lax cookies, path-scoped for the
  backoffice; the proxy-aware origin check runs *before* any credential is read, and
  that ordering is the tested property (`web/*/src/lib/gate.ts`). Customer assertions
  are HMAC-signed, compared constant-time *before* expiry is trusted, and never placed
  in cookies or rendered props.
- **Payments idempotency is the most hardened area.** Deterministic provider keys,
  bind-before-call with the money basis recorded at bind time, row-lock-serialized
  whole-vs-partial refund exclusion, resolve-before-submit refund adoption against
  Stripe, fail-closed on any ambiguity. Zero `float64` on any money path; fee splits
  are overflow-safe by construction.
- **Access lifecycle trail is genuine crypto.** Ed25519 with domain-separated,
  version-pinned canonical forms; kid injection refused; the verifier holds public
  keys only; QR and lifecycle keys live in enforced-distinct namespaces. Comments
  correctly refuse to claim rollback protection the design does not have (ADR-021).
- **NATS event handling follows ADR-017.** Envelope decoded first, schema floor
  enforced (`schema <= 0` terminated as poison), dispatch on schema before decoding
  `data`, unknown future schemas quarantined.
- **No debug surface.** No pprof, `/metrics`, or version endpoints. No CORS anywhere
  (correct: all frontends are same-origin behind the gateway). No `math/rand`, no
  `InsecureSkipVerify` in the repo. Logging never includes headers, bodies, tokens, or
  PII — the mail drainer explicitly refuses to log a reset body "because for a
  password reset the body IS a live credential"
  (`services/commerce/internal/mailer/drainer.go:109-121`).
- **Dependency audit clean.** govulncheck v1.6.0 across gateway, all 5 services, and
  shared/go: no reachable vulnerabilities (two module-level advisories — the
  unmaintained `x/crypto/openpgp` and a klauspost/compress s2 OOB read fixed in
  v1.18.7 — are not called by any code path; bump klauspost/compress opportunistically).
  `pnpm audit --prod`: no known vulnerabilities. CI already runs both plus trivy
  secret scanning.

## Recommendations

### Critical (Exploitable Vulnerabilities)

- [x] **S1** — **Scanner admission writes are unauthenticated.** `POST /api/access/scans`
  and `/scans/reconciliations` are public by contract (no `security:` in
  `services/access/api/openapi.yaml`) and the handlers check nothing before accepting
  a scan decision. Combined with the all-zero dev QR seed shipped as a compose default
  (S5), an attacker mints a QR payload that passes `ed25519.Verify` and redeems tickets
  at will; even without the key, replaying one captured QR burns a real ticket, and
  reconciliations rewrite scan history in bulk. The scanner README names the gap and
  defers it to TKT-19 — the deferral is the finding: today these routes are reachable
  through the gateway with no credential. Fix: put a distinct `X-Scanner-Token` on both
  routes (generated in the same env-bootstrap loop as the other credentials), or move
  them behind `/internal/` and have the scanner proxy through an authenticated SSR
  bridge. Until then the access service must not be reachable on any untrusted network,
  and the default QR key must not ship.
  File(s): `services/access/internal/api/server.go:48-49` (registration), `:172`, `:275` (handlers)

- [x] **S2** — **Ticket bundle and QR PNGs served on a bare, link-shared UUID.**
  `GET /api/access/orders/{ref}/tickets` and `…/qr.png` have no auth at all. The ref is
  `guest_order_ref` (122-bit entropy — not enumerable), but the system *treats it as
  shareable*: it is returned in checkout responses, wallet responses, and claim
  redirects, travels over plaintext HTTP, and lands in browser history and proxy logs.
  Anyone holding the URL — a forwarded "here are your tickets" message, a screenshot, a
  log line — has the full ticket bundle and printable QR codes, indefinitely, with no
  expiry or per-view check. Fix: require the HMAC customer assertion the wallet already
  uses (`services/commerce/internal/api/assertion.go`), or a per-order signed capability
  token with expiry; at minimum serve QR PNGs only behind short-lived signed URLs and
  stop returning the raw ref from public responses.
  File(s): `services/access/internal/api/server.go:46-47`, `:95-147`

### Important (Security Weaknesses)

- [x] **S3** — **Public order read discloses `status` + `customer_id` for any order UUID.**
  `GET /api/commerce/orders/{id}` is public by contract (`security: []`) and order IDs
  are *deterministic* — `uuid.NewSHA1(NameSpaceOID, "order:"+org+":"+idempotencyKey)`
  (`server.go:962`) — so anyone who knows the organizer id and a checkout idempotency
  key (both travel with the buyer's own request) can recompute order ids and poll
  payment status; `customer_id` doubles as an account-existence oracle. The code
  comment already names the fix (TKT-222: authenticated, ownership-scoped read that
  404s on mismatch, exactly as `listCustomerOrders` does). Until that lands, drop
  `customer_id` from the public payload.
  File(s): `services/commerce/internal/api/server.go:134`, `:1537-1561`

- [x] **S4** — **Back-office staff login has no rate limiting — the control named in
  ADR-042/TKT-195 was never wired.** `shared/go/ratelimit/ratelimit.go:5-6` documents
  the package as existing for catalog's back-office login, and `AuthenticateStaff`'s
  comment names TKT-195 as the control for submission volume — but no limiter is
  installed anywhere in catalog (zero non-test references). `POST
  /api/catalog/staff/authenticate` is reachable through the gateway with no per-account
  or per-source budget; bcrypt cost 10 blunts attempt speed but does not bound
  attempts, so credential stuffing is unlimited. This is a claim-vs-mechanism drift of
  exactly the kind AGENTS.md warns about: two comments assert a control that does not
  exist. Fix: wire `shared/go/ratelimit` around `AuthenticateStaff` with the same
  dual-key (subject + source) pattern commerce uses, or re-scope the ADR claim.
  File(s): `services/catalog/internal/api/staff.go:23-48`,
  `shared/go/ratelimit/ratelimit.go:5-6`, `services/commerce/internal/api/ratelimit.go` (pattern to copy)

- [x] **S5** — **Public signing keys ship as active compose defaults.**
  `JOURNAL_SIGNING_KEY:-local-development-journal-key` (compose.yaml:254),
  `ACCESS_QR_PRIVATE_KEY:-AAAA…` — an all-zero Ed25519 seed (compose.yaml:334) — and
  `ACCESS_LIFECYCLE_PRIVATE_KEY:-AQID…` — a `0x01..0x20` counter seed (compose.yaml:309,
  345) all boot silently when env is unset. A forged QR passes gate verification (S1
  becomes trivial); a forged lifecycle checkpoint passes `access verify-lifecycle`. The
  repo already solved this exact problem for the bearer tokens (no default, fail fast,
  retired literal refused — TKT-83); the three signing keys were left out of that fix.
  Fix: generate all three in the `env-bootstrap` loop (Makefile:163-171), require them
  with `${VAR:?}`, and have the binaries refuse the known dev values at startup,
  mirroring `retiredInternalToken`.
  File(s): `compose.yaml:254,309,334,345`, `Makefile:163-171`

- [x] **S6** — **No HTTP security headers anywhere.** Repo-wide, the only security
  header set is `Referrer-Policy: origin` on one page. No CSP, no `X-Frame-Options`,
  no `X-Content-Type-Options: nosniff`, no HSTS — nothing at the gateway, in either
  Astro middleware, or in the scanner's nginx.conf. Every storefront/back-office page
  is frameable (clickjacking the seat picker or a staff form), and the absence of CSP
  removes all defense-in-depth against the storefront XSS the session code itself names
  as the assertion-theft escalation path (`web/storefront/src/lib/session.ts:29-31`).
  Fix: one header middleware at the gateway (`X-Content-Type-Options: nosniff`,
  `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin`, a starter CSP per app
  class; HSTS once TLS exists) plus `add_header` in `web/scanner/nginx.conf`. Heed
  TKT-226: do **not** set `no-referrer` on the reset-password page — the origin gate
  needs the header.
  File(s): `gateway/cmd/gateway/main.go:156-159`, `web/backoffice/src/middleware.ts:59`,
  `web/storefront/src/middleware.ts:55`, `web/scanner/nginx.conf:1-24`

- [x] **S7** — **No rate limiting on holds, reservations, checkout, or scans.**
  The only limiter in the platform guards commerce's customer-credential surface.
  `POST /holds`, `POST /reservations`, `POST /orders`, and `POST /scans` are unlimited.
  For a system whose domain includes high-contention on-sales, an unauthenticated
  caller scripting the gateway directly can churn holds at line rate (each reserving
  stock for `HOLD_TTL`=10m) — the canonical inventory-hoarding / denial-of-sale bot
  pattern. Fix: per-source limiters on `POST /api/commerce/reservations` and `/orders`
  at minimum (accepting the documented XFF-collapse caveat), plus bounded hold
  concurrency per buyer. This may be a deliberate testbed gap — if so, pin it in an
  ADR rather than leaving it silent.
  File(s): `services/commerce/internal/api/server.go:132-134`,
  `services/inventory/internal/api/server.go:93-96`, `services/access/internal/api/server.go:48-49`

### Suggestions (Hardening)

- [x] **S8** — **One shared static token opens every service's money surface.** All five
  services hold the same `INTERNAL_SERVICE_TOKEN` (compose.yaml:32, shared `&go-env`
  anchor), and every payments mutation — charge, void, refund, partial-refund — keys
  off it with no per-organizer scoping. Compromise of any one service (or a smoke-suite
  config, or shell history) yields the whole platform's money surface. Fix: per-caller
  internal credentials or mTLS; at minimum split payments' token from the shared one as
  the staff write tokens already are.
  File(s): `compose.yaml:32`, `services/payments/internal/api/server.go:80-82`

- [x] **S9** — **~17 internal-token comparisons use `==` instead of constant-time
  compare.** The codebase already knows the right answer — `credentialMatches`
  (`services/commerce/internal/api/staff_credential.go:48-53`) uses
  `subtle.ConstantTimeCompare` and fails closed on empty — but catalog, inventory,
  payments, access, and commerce's own internal handlers compare with `==`/`!=`.
  Practical risk is low (the token is only reachable inside the compose network and
  timing over a network is hard), but the inconsistency is systematic. Fix: hoist the
  helper into `shared/go/httpx` and replace every inline compare, preserving the
  fail-closed-on-empty guard.
  File(s): `services/catalog/internal/api/server.go:266,351,372,399,433,478`,
  `services/catalog/internal/api/cache_control.go:70`,
  `services/inventory/internal/api/operational.go:21`,
  `services/payments/internal/api/server.go:81`,
  `services/access/internal/api/refunds.go:29`,
  `services/commerce/internal/api/server.go:1402,1520`, `exchanges.go:56,587`,
  `cancellation_refunds.go:33,82`, `unclaim.go:30`

- [x] **S10** — **Inventory's `problem()` echoes raw `err.Error()` to clients, including
  on 500.** The default case leaks wrapped pgx errors (schema and constraint names) to
  anyone who can reach `/holds`. Contrast catalog's `writeStoreError`, which maps
  sentinels and answers `"internal error"` while logging the real one. Payments echoes
  `err.Error()` on several 400/409 paths too — bounded sentinels today, one wrapped DB
  error away from a leak. Fix: mirror the catalog pattern in both services.
  File(s): `services/inventory/internal/api/server.go:129-160`,
  `services/payments/internal/api/server.go:144,285`, `psp.go:327,339`,
  `partial_refund.go:71,76`; pattern: `services/catalog/internal/api/server.go:583-586`

- [x] **S11** — **Weak committed local DB credentials and broad loopback publishing.**
  `deploy/postgres-init` creates roles whose password equals the role name, and
  `POSTGRES_PASSWORD: postgres` is committed; postgres, NATS, Grafana, and all five
  services publish ports on 127.0.0.1, so any process on the dev machine gets superuser
  and can reach every `/internal/` surface directly (bypassing the gateway's edge-deny
  and forging `X-Forwarded-For` for commerce's limiter). The per-database
  `REVOKE CONNECT … FROM PUBLIC` hardening is verified and correct; the residual is the
  loopback trust assumption. Fix before any non-local deployment: real generated
  passwords via `${VAR:?}` like the tokens, and stop publishing service ports that only
  the gateway needs.
  File(s): `deploy/postgres-init/01-databases.sql`, `compose.yaml:66,68,91,167,185,206,249,326`

- [x] **S12** — **`NewStripe` accepts a non-HTTPS base URL.** Production hard-codes
  `https://api.stripe.com`, but nothing enforces the scheme — a config change to
  `http://` would send the secret key's Basic auth in cleartext. Fix: one-line
  `strings.HasPrefix(baseURL, "https://")` guard for non-test clients.
  File(s): `services/payments/internal/psp/stripe.go:34-39`,
  `services/payments/cmd/payments/main.go:150`

- [x] **S13** — **Pin the currency-exponent assumption before enabling a non-EUR
  currency.** The charge boundary hard-codes EUR (`server.go:218`) but the journal
  accepts any 3-letter code (`store.go:115`) and integer-minor-units silently assumes
  exponent 2 (JPY is 0, KWD is 3). Also consider requiring `Amount > 0` (not just
  `>= 0`) for money-moving journal fact types so the journal is self-defending if a
  caller-side quantity guard is ever bypassed.
  File(s): `services/payments/internal/api/server.go:218`,
  `services/payments/internal/store/store.go:115`

- [x] **S14** — **Health endpoints return per-check `err.Error()` when degraded.**
  `shared/go/httpx/healthz.go:38-39` can surface DB driver error text (including DSN
  fragments) to any unauthenticated caller; `/healthz/all` additionally enumerates the
  service inventory. Low impact while loopback-bound; fix by returning a static
  "unhealthy" per check and logging the detail server-side.
  File(s): `shared/go/httpx/healthz.go:38-39`

## Notes

- The Stripe adapter is hard-restricted to test-mode keys and there is **no inbound PSP
  webhook surface** — the forge-a-confirmation attack class has no target in this
  design. All PSP state is pulled server-side with same-key idempotent replays.
- Two module-level advisories from govulncheck are not reachable: GO-2026-5932
  (`x/crypto/openpgp`, unmaintained — imported but never called) and GO-2026-5841
  (`klauspost/compress` s2 OOB read, fixed in v1.18.7). Bump the latter with the next
  dependency batch.
- Session stores are in-process (restart signs everyone out) — documented and
  acceptable single-replica; re-visit before any second replica.
- Findings S1/S2/S3 restate gaps the repo already tracks (TKT-19, TKT-222) — this
  review's contribution is confirming each is real and exploitable as described, and
  rating S1/S2 critical under the current compose defaults.
