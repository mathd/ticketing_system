# TKT-348 capacity-capture investigation

**Evidence status: executed, six repetitions passed.** The orchestrator ran the disposable PostgreSQL probe on 2026-09-27. See [results.md](results.md) and the unmodified [observed JSON](observed.json).

## Question and scope

The question is whether a public GA hold can take capacity after a release before a waitlist claimant does. The source review below maps the current release and expiry paths. The probe forces one sequential order against Inventory's real PostgreSQL store and validated HTTP router. It does not measure random-race frequency, throughput, gateway or Commerce behavior, NATS, or seated correctness.

## Verified source map

`liveClaims` in `services/inventory/internal/store/store.go` is the shared capacity predicate: a held claim counts when `expires_at IS NULL OR expires_at > now()`, and a `finalizing` claim always counts. The schema makes operational claims non-expiring. Buyer and group expiry therefore become available by PostgreSQL time without a scheduled release event. `sweepExpired` later writes `expired`, appends `claim_history`, releases terminal seat rows, and reconciles a draining capacity cut, inside its caller's pool-locked transaction.

For an unchanneled public hold, `CreateHold` locks the pool, sweeps expiry, sums confirmed and live-held quantity, then adds the unused remainder of active allocations from `reservedForChannelsSQL`. A released unit is not by itself a public unit: the new request must fit `COALESCE(target_capacity, capacity)`, current demand, and any still-active channel reservation. A channel-specific request must fit the same global target or physical limit, its allocation cap, and its sales window; seller and unlock-code checks also apply when configured. An allocation cap cannot override the pool limit. `Availability` is a display read; `CreateHold` performs its own locked admission check.

The seated paths were checked before making scope claims. `CreateSeatHold` and `CreateBestAvailableSeatHold` lock the same pool first, sweep due claims and claim named seats or select a contiguous run from the seat map. They do not use GA quantity admission or channel allocations. Full seated refund returns are supported; `ReturnRefundedCapacity` refuses partial seated returns because no ticket-to-seat subset mapping exists. This spike makes no seated-offer correctness claim.

## Probe command and assumptions

From the repository root, the orchestrator can run:

```sh
bash docs/evidence/TKT-348/run.sh /absolute/path/to/TKT-348-probe.json
```

The runner copies `services/inventory` and `shared/go` into a disposable temporary module tree, adds the probe there, and invokes the actual embedded Inventory migrations. It starts one unique container with the exact pinned Postgres image in `compose.yaml`, publishes only a random loopback port, and removes only that named container and its own temporary directory on exit. Six repetitions use separate temporary database schemas. The schema copy keeps Go `internal` imports valid without touching repository source.

Each repetition creates a GA pool with capacity five and places a five-unit operational hold. A validated `api.Server.Router(..., true)` receives a public `POST /holds`; the expected capacity refusal is checked. The real `ReleaseOperational` method returns one unit. Then ordinary public request A is awaited before ordinary public request B, each with a fresh idempotency key. The probe expects A to receive HTTP 201 and B to receive the actual capacity HTTP 409. It records response bodies, the claim rows, pool counters, and whether `confirmed + live held/finalizing <= capacity` holds.

There are no ordering sleeps. This sequence is a forced public-first counterexample only. It does not prove a random race's win rate or establish a waitlist guarantee. Any DB, migration, router, request, timeout, unexpected HTTP result, or invariant error terminates the run with a non-zero exit; the probe does not translate such failures into capacity refusals. The output file is written only after all six repetitions succeed. The runner's Postgres readiness polling is startup readiness, not part of the request ordering.

The probe does not start a listening socket. `httptest` calls the actual validator-wrapped router in process. It has real database-backed admission but omits gateway routing and inter-service deployment.

## Comparison against TKT-38 conditions of success

Parent TKT-38 defines these conditions verbatim:

1. "Freed inventory triggers a time-boxed offer to the head of the waitlist; expiry cascades to the next"
2. "Waitlist honors per-event purchase limits and account requirements"
3. "Waitlist-to-purchase conversion is traceable end-to-end (ADR-003)"

An after-release public race cannot meet the first condition as a priority contract. The probe shows only that this ordering is possible. A waitlist-first design needs a capacity decision at the Inventory lock boundary; sending a Commerce or NATS request while holding that lock would add a cross-service failure and latency path to the hot transaction.

The two approaches differ at the admission boundary. A release may commit a durable reconciliation marker without creating a capture in that transaction. Public admission must reconcile due sources and materialize captures under the pool lock before it can consume the released quantity. A quiet-pool worker must also run reconciliation, so expiry or scheduled allocation release can create a capture without a later write. Commerce later selects the eligible queue head and delivers the offer. In after-release competition, Inventory commits an ordinary public unit first and only then can Commerce discover it; a distinct public request can consume it before the waitlist request. The executed probe tests the latter order, not the proposed capture mechanism.

## Proposed recommendation, not tested behavior

Keep waitlist membership, priority, buyer eligibility, and offer delivery in Commerce, where the order and account policy live. Keep inventory admission and capacity capture in Inventory. This is a proposed contract, not a feature present in the repository, and the probe did not exercise it.

Commerce owns the queue, but Inventory needs local, authoritative activation and demand state before it can decide whether to protect public capacity. Commerce must publish a per-pool generation and conservative demand snapshot to Inventory. Inventory acknowledges and durably stores that generation under the pool lock. An enrollment receives waitlist priority only after that acknowledgment; a Commerce-only queue write is not active for admission. The activation record must identify whether eligible demand exists and its generation, without storing buyer PII. If Commerce is unavailable, Inventory uses the last acknowledged state. While it says demand is active, Inventory continues to protect eligible public headroom and public admission excludes pending captures. This preserves acknowledged priority but can leave capacity unused until Commerce recovers and updates the generation. If local activation state cannot be read or safely maintained, admission fails closed. No timely cross-service message is assumed.

The quiet-pool worker must invoke a bounded Inventory reconciliation command. Under the pool lock, that command materializes due buyer/group expiry and scheduled channel give-back captures; it must not only read captures that some later sale happened to create. Refund, operational release, capacity raise, and explicit claim-release transactions must durably mark their pool for reconciliation in the same transaction. A separate durable due-pool scan must find elapsed buyer/group expiries and scheduled channel give-backs by their database predicates, including when no later write touches the pool. Discovery and retry must run independently of future sales, across restarts, and without an Inventory domain event. ADR-072 denies Inventory `platform.*` publish rights, so Commerce polls/reconciles durable Inventory state after commit. Bound rows and work per hot-lock pass, persist enough progress to resume, and let repeated commands converge idempotently. A fresh public admission can proceed only after reconciliation confirms that no due source remains unprocessed; if a work bound leaves due work outstanding, preserve completed maintenance and return retryable maintenance-incomplete for that fresh admission. Existing replay branches return before this general maintenance because they admit no new demand.

Fresh public admission needs a transaction boundary that preserves maintenance work when the requested hold is refused. Keep the existing replay branches before general bounded maintenance: a matching live or terminal row returns its existing result, and a fingerprint mismatch returns `ErrIdempotency`, without requiring reconciliation to finish. A matching held-and-elapsed row keeps its targeted expiry/history/availability commit and `ErrConflict`; add a durable due-pool marker to that same commit so the worker can capture newly eligible headroom later. This targeted expiry does not require draining all due work. Preserve database and internal errors if that commit fails. Only an absent key enters general maintenance and then a savepoint for request-specific work. Run channel and seller checks, presale redemption, and hold creation there. On a business refusal, roll back to the savepoint and commit maintenance/capture work before returning the refusal. If bounded maintenance cannot finish, return maintenance-incomplete for fresh admission only. Any error that prevents safe maintenance or its commit must prevent fresh admission; do not report a capacity refusal as though maintenance succeeded.

The proposal counts pending captures and issued-but-unconverted offers as existing demand. A capacity cut clamps physical capacity to at least confirmed demand plus live claims plus protected capture demand, while the requested target blocks new demand. Unused active channel reservations do not enter the cut floor. They are not held or sold units, though they continue to reduce headroom for new general public admissions and captures. Their caps can remain above physical free capacity after a cut; the proposal does not promise full usable channel capacity or reduce caps automatically. Global target/physical limits and each channel cap still constrain new channel demand. An issued offer remains reserved through a cut. Transfer to a buyer claim is quantity-neutral under the pool lock; if the offer claim already appears in `liveClaims`, do not count it again as capture demand. New capture uses the target during a drain, or physical capacity otherwise, after confirmed demand, live claims, active channel reservations, pending captures, and offered quantity not already in `liveClaims`. This is a proposed accounting contract, not current behavior.

Implementation must extend every capacity reader and mutator that handles these quantities. This includes capacity adjustment and reconciliation, GA and seated admission and availability, expiry and transition paths, operational and refund releases, group placement/draw-down, and channel-allocation release/replacement. Current `liveClaims`, `effectiveCapacity`, `reconcileCapacity`, and admission paths do not include capture demand. The extension is unimplemented and must be applied consistently; this proposal does not make existing code account for it. A channel-specific source is not general public headroom while its allocation remains active. Which sources may feed which waitlist, and channel-specific waitlist policies, remain open.

Use durable non-PII links through organizer/pool/entry/generation → capture → offer → claim → reservation → order. Persist the applicable links in Inventory history and Commerce audit trails, and retain them across retries, offer expiry/cascade, and recovery. Replays must resolve the existing generation and identity; an expired or stale identity must not create a fresh capture or allocate fresh capacity. An expired offer returns its capture to the same priority generation before Commerce advances to the next eligible entry. Exact FIFO, offer TTL, and partial-fill policies remain owner choices.

For lazy buyer or reservation expiry, the bounded reconciliation command or a later locked admission transaction must observe expiry and protect capacity before public admission. A read-only display query cannot promise priority. Scheduled channel release is observed by the active-allocation predicate rather than a fictional release event. Refund, operational release, and capacity raise have concrete transaction commits that can create durable discovery state. Partial seated returns remain unsupported; seated offers need separate policy and a design that respects seat identity.

This recommendation leaves owner policy open. The safety goal is that Inventory never admits public demand against capacity protected by an acknowledged active waitlist generation. The liveness cost is that stale active state or an unavailable Commerce service can over-reserve capacity and delay public sale until Inventory receives an acknowledged update. The proposal does not claim a throughput ceiling, waitlist delivery guarantee, exact schema, or seated correctness.

## Open owner choices

- Offer priority and whether every return/release source is eligible.
- Queue eligibility rules, account requirements, and whether a buyer must acknowledge eligibility before capture.
- Offer TTL and delivery channels.
- Partial fill, skip, decline, and expiry behavior.
- Per-event purchase limits and the point at which they are reserved or checked.
- Whether seated inventory participates, including the partial-return limitation.

No child story is promoted by this spike. The offer stories remain subject to these choices.
