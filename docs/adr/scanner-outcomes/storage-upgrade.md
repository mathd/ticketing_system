### 7. F1: the old-tab barrier and the cost of each option

#### 7.1 Owner-selected storage: shared database, version 3, D9 and D14-3

Delivery status: TKT-558 implements the shared-name version 3 barrier and drains the old connection before closure.

The old code explicitly opens version 2, E2; reads all queue rows and omits type, E7. No new field, sentinel, owner id, handshake, or broadcast that only new code reads can bind that old reader. Do not put a new Exit or new-format admission into its v2 queue.

Use the same database name and upgrade to version 3, retaining all old records and stamping their legacy format. The format classification is a real data migration; do not call this a no-op upgrade. No new rows are minted before the compatible open completes. An old v2 connection prevents the upgrade; new code reports the barrier and does not accept scan presentations. When the old connections close and the upgrade succeeds, an old v2 open cannot read the upgraded database. This is the version-barrier design recorded in TKT-399 history D18 and implemented in B:`web/scanner/src/occurrences.ts:293-386`. Its behavior has **not been executed in TKT-556**. A rollback to the old bundle needs a forward-compatible storage reader or must fail closed until the new client returns. Do not delete the database to make rollback appear to work.

New clients cancel pending startup continuations on version change, attempt pending repairs on the still-open connection, then close after those attempts settle, D27. Existing minted scans retain their coordinator and transaction observation; close alone cannot suppress an in-time completed mark, A01. Session cancellation is separate C01. Their page coordinator and owner lock remain alive. Do not close first and then try to repair through that closing connection. Failed repair keeps the live lock and decision; page loss before a later successful repair leaves P. Closing a connection does not cancel a transaction already running. Upgrade can therefore wait for a transaction even after the version-change callback; P4-3 must stay visible.

#### 7.2 A real option without bumping the existing database

A separate database name can isolate all new-protocol records from an old reader. Create that new database at its initial version; keep the existing v2 database unchanged. The old bundle's fixed-name read cannot discover the new queue through its existing code, E2/E7. This is reasoning from the read paths, **not verified by a new implementation or browser test**. It refutes the overbroad historical phrase "a version bump is the only real barrier": that is true only if both versions keep the same database name and readable store.

This option costs two queues and a migration/rollback procedure. Define who drains existing legacy QUEUED rows and how the operator sees both queues. Do not bulk-copy PENDING rows while an old page is active. Keep owner-lock names compatible if a new client ever touches old owned rows. The safest initial isolation design leaves legacy PENDING recovery with the legacy client; new code may import only already-QUEUED legacy facts with unchanged ids, with idempotent Access replay. The duplicate-drain, legacy-lock failure, and rollback procedures are **not designed or verified here**. That work is an alternative storage ticket, not a hidden addition to the chosen version-3 ticket.

A separate name prevents F1 without making the old page stop scanning entries. It therefore loses the shared-version device-wide fail-closed behavior. Operators can still have two active scanner generations. Never claim that the new client has fixed the old client's P7-1 or other behaviors. Changing the key prefix or adding fields inside the old readable store is not isolation: the old listing reads every QUEUED row, E7. A server capability check alone cannot restore an Exit after the old serializer has already dropped its type. Refusing all old client traffic would require a separate server/client rollout and handling of legitimate old Entry queues; no such capability is verified here.

Owner D14-3 selected the version-3 barrier for one queue and preserved records. The separate-name discussion records a rejected alternative and its unverified costs. It is not an open owner choice or an implementation path for this delivery.

#### 7.3 Do not turn open completion into permission to resume a scan, D10

Delivery status: ticket 2 for readiness; ticket 3 for the time bounds after readiness. **Partial delivery:** TKT-558 implements Entry/storage; TKT-559 implements Entry timing and stalled-body deadlines. TKT-399 implements Exit.

Initialize storage independently of scan input. Until a compatible database, owner lock, and recovery are ready, disable both manual submission and camera detection; display "Scanner storage is not ready. No ticket was checked." On an explicit attempt during a readiness transition, finish it as S01; do not buffer the credential for later mint. On readiness completion, enable a fresh presentation only. On version change or storage failure, reset readiness and cancel old startup continuation generations. Retain a minted scan's decision and transaction evidence until it settles. A version-change callback alone must not invalidate an in-time completed mark.

A blocked event is useful feedback, but new tab B can wait behind new tab A without receiving it, as the TKT-399 thread records. Each page must show readiness progress independently. A 3000 ms startup notice may change to operator-action copy, but it is not a permit, a scan deadline, or proof that IndexedDB cancelled its open. An abandoned open request must close a connection if it succeeds later and must never publish readiness or continue an old scan. Close such late connections even after a newer retry succeeded. Do not keep an indefinitely pending open as the only cached store promise after a scan was stopped.

The IndexedDB request queue is scoped to storage key and database name, per corrected TKT-399 finding P3-3. A tab-local set cannot govern another tab's request queue. None of the 3000/30000/1000 ms values is a measured device performance allowance. Readiness prevents delayed mint caused by initialization; I4 still bounds awaits after readiness. The chosen barrier therefore does not depend on an open timer to enforce TKT-399 D30.

#### 7.4 Legacy rows need an explicit classification, owner D13-3

Delivery status: TKT-558 implements M01/M02 classification, retained export and held-row acknowledgement.

Stamp existing v2 rows during upgrade as the known legacy format. Under owner D31, existing legacy QUEUED rows retain main's queue eligibility even when their unknown producer was a live 401 or a decided response; serialize a normal legacy row with no own direction as Entry by omitting event type. A legacy refusal sends only local decision. For a normal legacy row, if direction is an own property, validate it: entry/exit is explicit; an unknown nonempty string stays nonempty for per-row rejection; own undefined, null, empty, or non-string becomes the nonempty invalid sentinel. Never use nullish or truthy fallback. A new-format normal row must have direction; absence cannot borrow the legacy default. Access's empty/default and unknown-value branches are `services/access/internal/api/server.go:684-693`.

D31 is literal about pre-upgrade QUEUED. Main can produce these rows from the generic offline catch, including body-first fallback after decided 409/422, accepted 200 or 500, from live 401 including a DB-outage 401, from foreign/reload PENDING recovery. Main's markQueued separately accepts any prior state, `web/scanner/src/occurrences.ts:311-313`; no reaching App path from ACT was found. Main also mints local refusals as QUEUED. P10 distinguishes observed call paths from that store capability. Rows have no cause field. The outcome is **possible false facts, indistinguishable**. Keep their ids in the D25 local export for review. The export distinguishes the M01 held set from the M02 sync-eligible set; listing an M02 id does not hold it or convert it into a proved admission. Preserve its class and state in the export, including if ordinary sync has since retired it. Retain the legacy row/id locally; the export is a local review aid, not Access evidence.

A legacy PENDING row is different. It cannot tell whether the old page received a rejection, chose offline admission, or lost its page before an answer. The old store releases its owner on connection close even if the page lives, E4/E5. Thus absence of an old owner's lock is not proof of actual old-page loss. A version upgrade does not reconstruct that lost local decision. Automatically recovering such a row would preserve P7-1 for the migration case.

Owner D13-3 accepts the legacy PENDING hold with an operator export/acknowledge path in this delivery. Never silently queue a held legacy row. Show an unresolved-record count. Ticket 2 includes the hold, unresolved count, warning, export, and acknowledgement together, D25. The v3 hold must not merge without that operator path. No "sync anyway" action exists.

Export an exact versioned local file of the held ids, credential, claimed times, state/type, owner/lease, format, and hold reason. Also list the ADR-085 D31 pre-upgrade QUEUED ids and class in that export, whether still queued or already retired by sync. Use separate held and legacy-queued lists. Acknowledgement applies to held rows only; legacy-queued ids remain sync-eligible under ADR-085 D31. Treat this as a local backup containing credentials. The export can expose ticket credentials if the operator shares or loses it; state that risk in the operator guide. Do not send it to an external service. Let the operator acknowledge selected ids only after requesting their export. Do not claim the browser proves the file was saved. Record acknowledgement time and disposition durably; retain the original row and exclude it from automatic sync. Acknowledgement removes it from the unresolved count, not from storage and not from the admission trail. Retrying export or acknowledgement must preserve ids and produce no Access request. A failed acknowledgement keeps the row unresolved. No deletion or credential-redaction export is part of this small path. TKT-558 implements this path and tests export, selected acknowledgement, failed acknowledgement, retained originals and M02 export after sync through the App and host Chrome. Browser download completion does not prove the file was saved to durable media.

Expected held count is a small transient set, not the whole old queue. M runs recovery on open and again in `queued()`, `web/scanner/src/occurrences.ts:174-200`, `:318-322`. Under successful normal opens, eligible dead foreign rows have already become QUEUED. The expected PENDING remainder at upgrade is rows whose owner is still live or whose lease is not yet eligible. This is an expectation from code, **not a measured count**; failures or unusual legacy data can leave more. Display and export the actual count, with no hard-coded limit or assumption that it is zero.

M01 does not claim to control an old client before the compatibility barrier completes. In particular, an aborted migration leaves old v2 clients with their existing recovery behavior. The new client must not scan or sync on that failed readiness path. No in-memory-only hold is an adequate substitute for the format classification.

Store tests must seed literal legacy PENDING, QUEUED, ACTUATED, and refusal rows in v2, perform the production upgrade, and read their exact identity/time/state. QUEUED remains drainable, PENDING stays held even when its old lock is absent and its lease expired. Mutation: use ordinary dead-owner recovery on a legacy PENDING row; the test must turn red. A second positive test recovers a new-format PENDING row only after actual coordinator destruction. This separates controlled new-format recovery, with its named false-fact residual, from held unknown legacy PENDING. D31's M02 fixtures must be literal stored shapes, not labels for historical causes. Cover normal and local-refusal rows; ownerId present/absent crossed with lease present/absent, including future/expired leases; actuated true/false; result present/absent; and normal-row direction own-property classes absent, own undefined, null, empty string, number, unknown nonempty string, entry and exit. Keep refusal-only serialization independent of a direction-looking property. QUEUED+actuated:true is a shape case, not a proved reaching App path. Assert exact id/time, retained shape, sync eligibility, serialized normal/refusal type and export membership before and after sync retirement, including per-row rejection of invalid directions. The store cannot test whether a row came from DB-outage 401, body-first fallback or real offline admission; no cause field exists. D31 accepts these causes as indistinguishable. Store tests cannot claim per-producer coverage. Pin the accepted false-fact possibility in a separate actual Access readback case. Mutating M02 into a hold, dropping its export id or claiming its cause is known must fail the corresponding fixture.
